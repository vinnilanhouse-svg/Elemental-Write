# Supabase e Vercel

## Aplicação no projeto existente

1. No SQL Editor do Supabase **hnhygaqrkiuaktuxfewh**, execute todo o arquivo `supabase/migrations/202611160001_cloud.sql` uma vez. Ou, com CLI autenticada e acesso administrativo: `supabase link --project-ref hnhygaqrkiuaktuxfewh` e `supabase db push`.
2. Em Authentication → Providers → Email, habilite e-mail/senha e **Confirm email**. Configure SMTP de produção, remetente, limites de envio e política de senha (mínimo 8 caracteres). O fluxo padrão usa links do Supabase e PKCE; abra confirmação/recuperação no navegador que iniciou o pedido. Depois da confirmação, outros dispositivos podem entrar normalmente com e-mail/senha.
3. Em Authentication → URL Configuration, defina **Site URL** como a URL HTTPS de produção da Vercel (ou domínio próprio). Em **Redirect URLs**, inclua a URL exata com `/` final de produção e `http://localhost:5173/` para desenvolvimento. Se necessário, adicione URLs de previews confiáveis explicitamente. Confirmação, recuperação e alteração de e-mail retornam a `window.location.origin + '/'`. Não é necessária rota de callback separada. Mantenha os templates padrão com `{{ .ConfirmationURL }}`.
4. Publique a função: `supabase functions deploy delete-account --project-ref hnhygaqrkiuaktuxfewh`. Configure `APP_ORIGINS` com origens permitidas sem barra final, separadas por vírgula, por exemplo `https://seu-dominio.vercel.app,http://localhost:5173`. Pelo CLI: `supabase secrets set APP_ORIGINS=https://seu-dominio.vercel.app --project-ref hnhygaqrkiuaktuxfewh`. A plataforma fornece `SUPABASE_URL` e `SUPABASE_SERVICE_ROLE_KEY` à função. **Nunca coloque service_role em variáveis VITE ou no frontend**. `supabase/config.toml` delega a verificação do JWT ao próprio handler para suportar as chaves assimétricas atuais do Auth; chamadas sem um token validado por `auth.getUser()` são rejeitadas. A função valida o JWT no servidor, exige autenticação por senha nos últimos cinco minutos e deriva o usuário do token; não aceita um ID de usuário do cliente. A exclusão em auth.users apaga os registros associados por cascata.
5. Na Vercel, configure `VITE_SUPABASE_URL` e `VITE_SUPABASE_PUBLISHABLE_KEY` com os valores públicos de `.env.example`, nos ambientes desejados. Build `npm run build`, instalação `npm ci`, saída `dist`, Node 22.12+ e branch de produção `main`. Reimplante após configurar as variáveis. Sem elas, o app inicia em modo local. A CSP permite apenas a origem Supabase especificada; se trocar o projeto, atualize `vercel.json` e `localhost/security-headers.json`.

A chave pública permite o cliente usar Auth e as políticas RLS, mas não permite criar tabelas, configurar Auth, publicar funções ou configurar a Vercel. Essas ações exigem um administrador autenticado nas plataformas. Não é preciso fornecer segredos no chat.

## Dados, sincronização e recuperação

`ew_profiles` armazena preferências, `ew_projects` o objeto completo de projeto (incluindo capa e ícone), `ew_documents` o objeto completo de roteiro/nota (incluindo marcas e espelho). JSONB preserva todos os campos existentes; chaves relacionais asseguram propriedade e cascatas. O RPC de salvamento compara e incrementa revisão em uma única transação; conflitos preservam o texto e exigem exportar/reconciliar. A capa também compara a versão anterior. O servidor mantém a propriedade; RLS bloqueia outras contas.

Autosave serial após 650 ms sem digitação, a cada cinco minutos, manualmente e ao ocultar/navegar. “Salvo na nuvem” aparece após resposta do servidor. Em falha, o texto fica em memória e um rascunho por conta/documento é guardado em LocalStorage quando disponível. Uma edição durante uma gravação mantém a revisão correta do rascunho. Ao reabrir um documento, o rascunho é recuperado e tenta salvar; divergência de revisão gera conflito. Se o navegador não puder guardar o rascunho, o aviso pede manter a aba e exportar. Não há modo offline completo, colaboração ou mesclagem automática. Não limpe o navegador com dados pendentes.

A opção “Transferir projetos locais para a conta” pede confirmação antes de copiar projetos de todos os perfis locais da mesma origem. Cada projeto e seus documentos são importados atomicamente, com novos IDs e todos os campos preservados. A cópia local fica intacta. Se um projeto falhar, os anteriores já copiados permanecem; repetir a transferência cria novas cópias. É possível apagar cópias indesejadas depois de conferir o backup. Dados locais de outro navegador/domínio precisam ser exportados e restaurados manualmente primeiro.

## Validação reproduzível

- `npm ci --cache /tmp/elemental-npm-cache`, `npm test`, `npm run build`.
- `npm run test:cloud:sql`: executa a migração real em PostgreSQL via PGlite; verifica RLS com dois papéis autenticados, referências cruzadas, gravação/releitura, conflito, importação/exportação completa, rollback e cascata. As funções `auth.uid()`/`auth.jwt()` são fixtures locais, sem substituir as do Supabase em produção.
- `npm run test:cloud:edge`: executa o handler de exclusão com Supabase administrativo simulado; verifica origem, JWT inválido, senha recente, confirmação e uso exclusivo do ID autenticado. Não publica nem executa exclusão real.
- Inicie `npm run dev -- --port 5175` com as variáveis públicas definidas e execute `npm run test:cloud:browser`. HTTP do Supabase é simulado: cadastro/aviso de confirmação, recuperação, credenciais inválidas, login, sessão recarregada, transferência preservando IndexedDB e autosave com falha/recuperação. Inclui callbacks PKCE de confirmação/recuperação, nova senha, saída e consulta/correção/exportação/exclusão pela interface. Não prova entrega de e-mail, configuração remota ou funcionamento da função publicada.
- Sem variáveis de Supabase, inicie na porta 5173 e execute `npm run test:browser`, `BASE_URL=http://localhost:5173 npm run test:autosave`, `test:screenplay`, `test:production` e `test:icons`.

## Conferência externa necessária antes de liberar contas

Após aplicar a migração e publicar a função, use duas contas de teste confirmadas em navegadores separados. Cadastre, confirme pelo e-mail, saia e entre; recupere a senha pelo link e entre com a nova senha. Crie projeto com roteiro, nota, capa, ícone e espelho, edite e aguarde “Salvo na nuvem”; abra no segundo dispositivo com a mesma conta e confira. Na outra conta, confirme ausência dos dados da primeira e tente chamadas com IDs da primeira (leitura vazia, escrita bloqueada). Desconecte a rede, edite, confira erro e rascunho; reconecte e salve. Transfira dados locais e confira que continuam em IndexedDB. Corrija nome/e-mail, confirme o novo e-mail, exporte ZIP, exclua projeto e depois conta com senha; confirme remoção do Auth e tabelas, ausência em sessão antiga e preservação de outra conta. Revise logs sem registrar senhas ou tokens.

Nenhuma migração, configuração de Auth ou publicação de função é executada apenas pelo push ao GitHub. O deploy da Vercel depende da integração Git configurada no projeto. A validação real desses pontos permanece externa até haver acesso administrativo e de rede apropriado.
